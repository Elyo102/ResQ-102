## מה נבנה

התפקיד של המשתמש עבר מ**שדה במסמך Firestore** ל**Custom Claim
בתוך טוקן ההזדהות**.

לפני: כל בדיקת הרשאה הריצה `get()` מקונן — 4-5 קריאות מסמך
לכל פעולה, שגוגל מחייבת עליהן.

אחרי: אפס קריאות. כללי האבטחה קוראים ישירות מהטוקן.

מבנה ה-claims:

```
{ role, stationId, shift, code, super? }
```

בידוד בין תחנות דרך **נתיב**, לא דרך שדה:

```
stations/{stationId}/users/{uid}
stations/{stationId}/attendance/{docId}
```

**קבצים לסקירה:**
`functions/index.js` · `firestore.rules`
בריפו `github.com/Elyo102/station-102-Fire`

## חמש שאלות שאני רוצה עליהן דעה

### 1. השהיית טוקן מול ביטול הרשאה דחוף

טוקן מתרענן אצל גוגל אחת לשעה. אם קצין מושעה, ההרשאה שלו
נשארת תקפה עד שעה — אלא אם האפליקציה קוראת `getIdToken(true)`.

**האם צריך מנגנון ביטול מיידי, או שהחלון הזה מקובל למערכת
שמנהלת שעות ושכר?**

### 2. הקוד האישי בתוך הטוקן

הוספתי `code` ל-claims כדי שכללי הנוכחות לא יצטרכו `get()`.
החלופה: למפתח את הנוכחות לפי `uid` במקום לפי קוד אישי.

**איזו גישה עדיפה בטווח ארוך, כשיש כמה תחנות שבהן קודים
אישיים עשויים להתנגש?**

### 3. צוואר בקבוק תפעולי

הוחלט שרק מנהל-על מעניק תפקידים. עם 39 משתמשים זה סביר.

**עם עשר תחנות זה קורס. מה נקודת המעבר הנכונה, ואיך מאצילים
בלי לפתוח פרצה?**

### 4. דיווח חוצה-תחנות

בידוד דרך נתיב מקשה על שאילתות ארציות. הפתרון הוא
`collectionGroup` עם אינדקסים מוגדרים מראש.

**האם יש כאן חרטה עתידית שאני לא רואה? מתי כדאי להגדיר את
האינדקסים — עכשיו או כשיהיה צורך?**

### 5. סדר הבנייה

הסדר שנקבע: יסוד → כשירויות וקו אדום → נוכחות וחריגים →
פידבק → החלפות → שיבוץ → אנליטיקה → שכר → טפסים → תקלות רכב.

היעד: **כיסוי מלא של המערכת הישנה** לפני מעבר.

**האם הסדר הזה נכון בהינתן שהיעד הוא כיסוי מלא ולא MVP?
מה היית מקדים או מאחר?**
