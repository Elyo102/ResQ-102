## מה נבנה

הרשאות עברו מקריאת מסמך ל-Custom Claims בטוקן:

```
{ role, stationId, shift, code, super? }
```

`firestore.rules` גרסה 2.0 מכילה **אפס קריאות `get()`**.
בגרסה 1.1 כל פעולה עלתה 4-5 קריאות מסמך.

בידוד בין תחנות דרך נתיב: `stations/{stationId}/...`

## שש שאלות

### 1. סקירת חוקי אבטחה

עבור על `firestore.rules` ותחפש חורים. שים לב במיוחד ל:

- `attendance` — ניסיתי למנוע מכבאי לאשר לעצמו שעות
  ולשייך רישום לכבאי אחר
- `swaps` — ניסיתי למנוע ממקבל בקשה לאשר סופית
- `registration_requests` — משתמש חדש עדיין בלי claims

**האם יש מסלול שפספסתי?**

### 2. `token.get(key, default)`

השתמשתי בזה כדי שמשתמש בלי claims לא יפיל את הכלל בשגיאה.

**האם זו התנהגות מובטחת ב-rules v2, או שאני נשען על משהו
שעלול להשתנות?**

### 3. שאילתות list מול כללים ברמת מסמך

כללים כמו `resource.data.user_code == myCode()` עובדים על
`get` בודד. על `list`, Firestore דורש שהשאילתה תהיה מוגבלת.

**האם הכללים כתובים כך שהאפליקציה תוכל בכלל להריץ את
השאילתות שהיא צריכה, או שאני עומד לגלות `permission-denied`
רק בזמן אמת?**

### 4. עלות בקנה מידה

מודל: צבירה בכתיבה, קריאה שטוחה. מסך אחד = מסמך אחד.
`onSnapshot` רק לנתונים שפועלים לפיהם.

**39 משתמשים היום, יעד 3000. איפה זה נשבר כלכלית?
מה התקציב הנכון להתראה ב-Cloud Billing?**

### 5. App Check

טרם הוגדר.

**כמה דחוף למערכת עם נתוני שכר? מה נשבר אם מפעילים אותו
אחרי שכבר יש משתמשים?**

### 6. הגנות מסד נתונים

`Delete Protection` ו-`Point In Time Recovery` שניהם **כבויים**.

**מה עלות ההפעלה, ומה נכון להפעיל לפני שיש נתונים אמיתיים?**
